# 课程知识点与源码导读

更新日期：2026-10-12。适用于 LangChain v1、后端来源出题与学习辅导。本文按实际源码入口解释概念；学习环境与教材验证见 [学习准备与章节计划](学习准备与章节计划.md)，升级历史见 [三项升级测试用例与验收报告](三项升级测试用例与验收报告.md)。

## 1. 先看两条不同的调用路径

后端根目录是 `apps/api/study_agent/`。`api/routes/` 是目录；`api/dependencies.py` 和 `api/tutoring_dependencies.py` 是文件。前者提供数据库事务、存储和索引等依赖，后者的 `get_tutor_service` 组装辅导服务。教材中后端相对路径都需要加上这个根目录，不能在仓库根目录寻找 `dependencies` 文件夹。

阅读辅导时按 `apps/web/src/views/TutorView.vue::send → api/routes/tutoring.py::submit_message → application/tutoring.py::TutorService.submit → agents/tutor/agent.py::create_tutor_agent → agents/tutor/tools.py::make_tutor_tools` 跟踪。业务查询再进入 `application/learning_queries.py` 或 `application/retrieval.py`。一次只跟踪一种功能，不必先通读全部仓储。

界面左侧选择知识库，输入框上方选择问题类型；具体题目的上下文从答后“继续请教”绑定。`progress` 查询知识库累计统计，`mistakes` 查询最近 30 天错题，当前界面不支持指定某一轮诊断批次。没有具体已答题锚点，不等于没有学习历史。取证由工具读取业务记录或资料片段，引用有效性与建议本身是否正确仍是不同问题。

进度页现在显示已有知识点的真实名称；掌握度、复习计划和学习历史各自每页 5 条。知识点和复习列表在前端分页，历史在后端分页；顶部统计使用全部掌握度记录和历史响应的 `total`，不会随当前页变化。删除知识库的过滤仍保留，单次答对后显示 41% 是规则更新结果。

出题是受控 LCEL Chain：`Celery generate_questions → plan_generation_groups → 逐组 create_knowledge_point_chain / create_question_generation_chain → bind_question_context → validate_question_drafts → 不足时最多补充一次 → PostgreSQL / 题目索引`。模型只填内容，来源由后端绑定实际输入原文，步骤顺序由 Python 决定；它没有自主选择业务工具。因此 Structured Output 和工作流轨迹都不能作为 Agent Tool Calling 的证据。

学习辅导是单 Agent：`api/routes/tutoring.py → TutorService.submit → create_tutor_agent → 模型选择只读工具 → ToolMessage → 下一次模型调用 → validate_draft / revalidate → TutorRepository.complete`。源码已经按这条路径实现；具体测试结果见 [三项升级测试用例与验收报告](三项升级测试用例与验收报告.md)，本导读不替代验收。

业务判分另有确定性路径：`api/routes/study.py → StudyService → grade_question → 学习记录 / 掌握度 / 复习任务`。判分结果由程序计算，模型讲解在学习主事务之外运行，失败时使用来源绑定的降级讲解。

## 2. Model、Messages 与 Prompt

`apps/api/study_agent/llm/models.py::get_chat_model(settings, *, purpose)` 是统一 Model 入口。输入为服务端配置和用途，输出为 `BaseChatModel`；用途为 `question_generation`、`study_explanation` 或 `tutoring`。OpenAI-compatible 端点经过显式 provider adapter，辅导配置按字段继承公共配置。业务调用方不传任意 API key 或端点。

`apps/api/study_agent/question_generation/chains.py` 使用 `ChatPromptTemplate.from_messages` 创建 system / human 消息模板，`.partial(...)` 绑定 parser 的格式要求；运行时参数填充语言、知识点和资料片段。Prompt 内容不是业务授权，资料里出现的命令也不应变为系统指令。

`apps/api/study_agent/application/study_explanations.py::LangChainStudyExplanationGenerator` 使用同一模型入口生成答后讲解；无配置或调用失败时，通过 `fallback_explanation` 给出绑定题目来源的说明。

## 3. LCEL 与 Structured Output

`create_knowledge_point_chain` 输入 `{language, context}`，输出 `KnowledgePointBatch`。`create_question_generation_chain` 输入目标题数、允许题型、难度、语言、知识点序列和 context，输出 `QuestionBatch`。`prompt | model | parser` 是 LCEL 的 Runnable 组合；另一分支使用模型的 `with_structured_output`。两者都是受控 Chain。

`apps/api/study_agent/question_generation/schemas.py` 约束模型输出结构；`context.py` 选择小组原文并由后端绑定来源，模型不再填写片段 ID 和逐字引文。`quality.py::validate_question_drafts` 检查题型、难度、知识点、来源存在性和重复题干。基础校验通过不代表答案语义已验证，仍需人工审核。

`tasks.py::build_generation_context` 按字符预算依次拼接资料片段：后续片段超过预算时停止，首个片段保留原有行为；计数未包含片段之间的分隔符，首片段也可能超预算，因此不是严格的最终文本总长上限。这个名字描述生成输入，不能解释为已经实现长资料覆盖、分批出题、检索式出题或 LangChain 的运行 Context。可运行 `examples/learning/rag_context.py` 查看固定长材料的选取范围。

可运行用例：`tests/test_question_generation.py::test_three_question_types_pass_grounding_gate`、`test_grounding_gate_rejects_fabricated_quote`、`test_single_choice_schema_requires_four_options`。

## 4. Retriever 与两种 Index

资料索引入口是 `ingestion/factory.py::get_document_index`，题目索引入口是 `question_generation/factory.py::get_question_index`。`api/dependencies.py` 使用同名、不同返回协议的依赖包装器，并给工厂导入加明确 alias，避免资料索引和题目索引含混。

`ingestion/vector_index.py::MilvusDocumentIndex` 返回候选资料命中。检索的业务结果还必须通过当前 PostgreSQL 资料状态和范围复核，向量 ID 存在不意味着资料仍有效。辅导共享检索的 `application/retrieval.py` 在本次集成中核对；不要把索引 adapter 当成整个授权和引用校验边界。

## 5. Context、State、Snapshot 与 Checkpointer

`agents/tutor/context.py::TutorContext` 是冻结 dataclass，包含服务端固定的知识库、会话与轮次 ID、已作答题锚点和 intent，通过 `ToolRuntime[TutorContext]` 注入；模型参数 Schema 不包含知识库或线程 ID。`agents/tutor/state.py::TutorState` 扩展 `AgentState`，保存标准 messages、本轮 evidence/flags 与 turn ID。调用预算由每轮新建的 `middleware.py::RunBudget` 管理，不与长期数据库统计混存。

`domain/ports.py::LearningSessionSnapshotStore` 和 `infrastructure/study_state.py::RedisLearningSessionSnapshotStore` 是现有学习会话快照缓存。Redis key 仍为 `study:session:{session_id}:state`。缓存缺失、损坏或 Redis 故障时，业务可从 PostgreSQL 重建；快照不是 LangGraph Checkpointer。`StudyService` 的 `state_store` 参数为兼容现有调用保留，但其类型已使用明确的 Snapshot 协议。

`infrastructure/checkpointer.py::open_tutor_checkpointer` 在生命周期中管理 PostgreSQL saver 与独立辅导锁连接池；`setup_checkpointer` 通过部署命令显式创建框架表。API 启动只读探测。`TutorService.submit` 从已接受 checkpoint 指针开始，用已提交业务消息重建用户/助手历史，并重置本轮证据。`TutorRepository.complete` 在短事务中提交最终消息、轮次状态和接受指针。`recover_locked` 只接受匹配轮次的完整草稿，经重新验证后提交；不完整中断标失败，显式新 ID 重试。

可运行用例：`tests/test_reliability.py::test_corrupt_learning_snapshot_is_cache_miss`。它只验证 Redis 快照损坏的处理，不验证辅导检查点恢复。

## 6. Workflow 轨迹与真正的 Tool

`infrastructure/models.py::WorkflowRunModel` / `WorkflowStepModel` 映射到历史 `agent_runs` / `agent_steps`，表名、字段、外键和历史行保留。物理字段 `agent_type` 是兼容字段，不能仅从字段名判断实现是否有 Agent。

出题新运行的 `input_summary.execution_kind` 为 `chain`，步骤 `tool_name` 为 `None`。历史行里的 `tool_name=langchain_structured_output` 是原 parser 步骤标记，不能作为业务工具调用证据。辅导的新运行应由实现标记 `execution_kind=agent`，并记录实际工具选择、结果和验证。

`agents/tutor/tools.py::make_tutor_tools` 定义 `search_learning_materials`、`get_answered_question_context`、`get_learning_progress`、`list_recent_mistakes`，查询通过 application 层完成。工具返回 `Command` 更新证据与带匹配 call ID 的 `ToolMessage`。`middleware.py::TutorBudgetMiddleware` 与框架调用限制约束模型、工具、检索次数、结果大小和执行期限。`agent.py::create_tutor_agent` 装配 `ToolStrategy(TutorAnswerDraft)`，格式修复最多一次。

最终 `validation.py::validate_draft` 检查必需取证标记与本轮证据 ID；`application/retrieval.py::revalidate` 在提交前复核当前资料归属、ready 状态、内容哈希及引文。学习时应结合 `tests/test_tutor_agent.py` 的真实 create_agent＋脚本化模型循环，观察 Model → Tool → Model；脚本化结果不代表真实供应商能力。

## 7. 命名迁移与兼容窗口

生产代码和现有测试已使用 `LearningSessionSnapshotStore`、`RedisLearningSessionSnapshotStore`、`WorkflowRunModel`、`WorkflowStepModel`、`validate_question_drafts`、`create_knowledge_point_chain`、`create_question_generation_chain` 和 `build_generation_context`。

短期 alias 保留旧类、旧链工厂、旧校验函数和旧 FastAPI dependency 名称，供尚未迁移的外部导入及依赖覆盖使用。alias 指向同一个对象，不额外注册 ORM mapper，也不生成第二个 FastAPI 依赖身份。下一个内部接口清理阶段在确认下游已迁移后移除；不在本次迁移中更改公开 JSON 字段、路由、数据库物理名或 Redis key。

在 `apps/api` 中使用装有最终锁文件的 Python 环境运行：

```powershell
& '.\.venv\Scripts\python.exe' -m pytest tests/test_question_generation.py tests/test_reliability.py tests/test_p1_api.py tests/test_p3_api.py tests/test_adaptive_learning.py tests/test_study_grading.py
```

这些测试覆盖题型结构、来源约束、缓存故障、HTTP 依赖和确定性学习行为。它们不等于真实 PostgreSQL、真实模型或浏览器验收。`tests/test_postgres_reliability.py` 的集成用例需要显式指定隔离测试数据库；辅导测试从 `tests/test_tutor_agent.py`、`tests/test_tutor_acceptance.py` 与前端 `tests/e2e/tutor.spec.ts` 开始阅读，真实数据库、恢复和供应商结果按最终报告定位。
