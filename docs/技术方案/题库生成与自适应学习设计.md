# 题库生成与自适应学习设计

状态：P3 题库生成、P4 基础学习闭环和 P5 自适应选择/检索讲解均已实现  
原则：RAG 负责证据检索，LangChain 负责编排，学习 Agent 负责自适应决策，程序负责确定性写入

## 1. 为什么不把所有流程都称为 Agent

StudyAgent 的核心不是 Agent 数量，而是资料、题目、知识点、答题记录和复习计划之间能形成稳定闭环。

MVP 将核心智能能力分为两类：

1. 题库生成 RAG 工作流：离线处理资料，通过检索原文、结构化生成和质量门禁产出可验证、可溯源的知识点和题目。
2. 自适应学习 Agent：在线组织一次学习会话，选择下一学习动作、判题、解释并驱动掌握度更新。

题库生成更适合稳定的流水线，而不是让模型自由决定下一步。RAG 解决“从哪些原文获得依据”，LLM 解决“如何抽取知识点和生成题目”，LangChain 负责把 Loader、Splitter、Retriever、Prompt、Structured Output 和持久化步骤串起来。只有在线学习过程需要根据用户表现动态分支，因此保留为受控 Agent。

二者共享领域数据，但不能互相直接调用，也不通过自然语言协商。题库生成工作流负责“准备可靠学习内容”，学习 Agent 负责“使用内容安排学习”。

## 2. 共同约束

### 2.1 LLM 可以做什么

- 从文本中归纳候选知识点。
- 生成题目、参考答案、评分要点和解释。
- 判断开放题答案覆盖了哪些评分要点。
- 生成面向学习者的自然语言反馈。
- 在候选动作之间给出建议。

### 2.2 LLM 不可以做什么

- 直接执行 SQL 或修改数据库。
- 自行决定资源归属和访问范围。
- 自行生成不存在的片段 ID、题目 ID 或知识点 ID。
- 跳过结构化输出和业务校验。
- 自行把分数写成超出题目满分的值。
- 自行改变掌握度算法或复习日期。
- 把模型输出当成事实而不验证原文证据。

### 2.3 工具调用规则

- Agent 只调用有类型声明的工具。
- 工具输入输出使用 Pydantic 模型。
- 查询工具只读；命令工具由 application service 执行事务。
- 每次运行记录模型、Prompt 版本、工具调用、输入摘要、输出、耗时、Token 和错误。
- 同一运行需要 `run_id` 和幂等键，避免重试产生重复题目或重复答题记录。

### 2.4 LangChain 的使用边界

LangChain 是本项目统一的 LLM 与 RAG 应用框架，具体使用在：

- `Document Loaders`：把不同资料解析结果转换为统一 `Document`。
- `Text Splitters`：按标题和 Token 长度切块并保留 metadata。
- `Embeddings`：封装本地、TEI、OVMS 或 OpenAI-compatible Embedding。
- `Milvus VectorStore`：写入原文与题库向量，并执行 metadata 过滤。
- `Retriever`：为知识点抽取、题目生成、错题讲解和自由问答提供证据。
- `PromptTemplate`：集中管理不同阶段的 Prompt 和版本。
- `with_structured_output` / Pydantic Parser：约束知识点、题目和判题结果；当前 DeepSeek 推理模型使用兼容性更好的 `PydanticOutputParser`。
- `RunnableSequence`、`RunnableParallel` 和重试包装：编排固定的生成与验证链路。
- Callback：记录 Token、耗时、模型和 Trace。

领域对象、数据库事务、掌握度算法、SM-2 和会话状态机不依赖 LangChain，避免框架侵入核心业务。

## 3. 题库生成 RAG 工作流

### 3.1 职责

输入一份已经解析的资料，完成：

- 基于章节和片段抽取知识点。
- 合并重复或高度相似的知识点。
- 为知识点规划题型、数量和难度。
- 从原始片段生成题目。
- 验证答案和解析是否被原文支持。
- 去除重复、低信息量和不完整题目。
- 保存通过质量门禁的题目及引用关系。

它不负责底层文件格式解析，也不负责学习者掌握度。文件解析器先产生 LangChain `Document`，RAG 工作流从 Document 和 Milvus 检索结果中构建生成上下文。

### 3.2 输入

```python
class QuestionGenerationInput(BaseModel):
    job_id: UUID
    knowledge_base_id: UUID
    material_id: UUID
    target_question_count: int = Field(ge=1, le=100)
    allowed_types: list[Literal["single_choice", "fill_blank", "true_false"]]
    difficulty_range: tuple[int, int] = (1, 3)
    language: str = "zh-CN"
```

### 3.3 状态

```python
class QuestionGenerationState(TypedDict):
    run_id: str
    material_id: str
    chunk_ids: list[str]
    knowledge_point_candidates: list[dict]
    knowledge_point_ids: list[str]
    blueprint: list[dict]
    question_drafts: list[dict]
    accepted_questions: list[dict]
    rejected_questions: list[dict]
    retry_count: int
    status: str
```

状态只保存 ID 和结构化数据，不把整份文档或大段上下文放入 checkpoint。

### 3.4 工具

#### `list_material_chunks`

按章节顺序返回片段 ID、页码、标题路径、Token 数量和短摘要。用于规划，不一次返回全文。

#### `read_chunks`

根据受控的 chunk IDs 返回原文。一次读取数量和总 Token 有上限。

#### `find_similar_knowledge_points`

查询当前知识库已有知识点，供合并和去重使用。

#### `save_knowledge_points`

接收通过 Schema 校验的知识点草稿，由程序完成 upsert，并返回真实 ID。

#### `find_similar_questions`

结合文本、知识点、题型和答案检索候选重复题。

#### `validate_question_grounding`

程序化检查引用片段存在、答案非空、选项合法、分数范围合法；必要时调用第二次模型验证答案是否能从原文推出。

#### `save_questions`

只保存通过全部门禁的问题，并在同一事务内保存 `question_sources`。

### 3.5 工作流

```text
load_manifest
  → group_chunks_by_section
  → retrieve_supporting_chunks
  → extract_knowledge_points
  → merge_knowledge_points
  → build_question_blueprint
  → generate_question_batch
  → schema_validation
  → grounding_validation
  → semantic_deduplication
  ├─ 不合格且可修复 → repair_question → 重新验证
  ├─ 不合格且不可修复 → reject
  └─ 合格 → persist
  → summarize_job
```

MVP 使用 LangChain Runnable/LCEL 编排固定步骤，结合 Celery Chain 执行长任务。需要并发处理章节时使用 `RunnableParallel` 或 Celery Group；修复循环由普通 Python 控制，最大修复次数为 2，超过后拒绝，不允许无限自我修正。当前阶段不引入 LangGraph。

### 3.6 题目 Schema

```python
class GeneratedQuestion(BaseModel):
    knowledge_point_key: str
    question_type: Literal["single_choice", "fill_blank", "true_false"]
    stem: str = Field(min_length=5, max_length=1000)
    options: list[str] | None = None
    correct_answer: str
    scoring_points: list[str] = Field(default_factory=list, max_length=8)
    explanation: str
    difficulty: int = Field(ge=1, le=5)
    source_chunk_ids: list[UUID] = Field(min_length=1, max_length=5)
    source_quotes: list[str] = Field(min_length=1, max_length=5)
```

额外程序规则：

- 单选题必须有 4 个互不重复的选项，并且正确答案必须命中其中一个。
- 填空题答案不允许是过长句子，必须给出可接受答案集合。
- 判断题答案只能是“正确”或“错误”，不生成多余选项。
- 引文必须是来源片段的真实字符串或规范化后可匹配文本。
- 题干不能要求依赖资料之外的时效信息。
- 同批次题目之间、与历史题库之间都需要做重复检查。

### 3.7 题目质量门禁

题目进入启用状态前必须满足：

1. Schema 合法。
2. 引用存在且属于当前资料。
3. 标准答案可由引用片段支持。
4. 题干表达完整，没有“根据上文”等丢失上下文的指代。
5. 题型结构合法。
6. 与现有题目的相似度低于阈值，或人工确认不是重复。
7. 知识点归属存在。

MVP 可将通过自动门禁的题目保存为 `draft`，由题库页面一次人工复核后切换为 `active`。为了演示完整链路，也可以提供“自动启用高置信度题目”的显式开关，默认关闭。

### 3.8 失败策略

- 单个章节失败不使整份资料回滚，记录失败章节并继续。
- 结构解析失败只重试模型输出，不重新解析文档。
- 引用验证失败优先重新选择片段，其次修复题目，最后拒绝。
- 数据库写入按批次事务执行，失败可用幂等键重试。
- 任务结束状态分为 `completed`、`partial`、`failed`。

## 4. 学习 Agent

### 4.1 职责

学习 Agent 管理一次学习会话：

- 根据会话模式加载目标和学习者状态。
- 选择当前最合适的知识点和题目。
- 展示题目并接收回答。
- 评分、解释和检索原文证据。
- 触发掌握度与复习任务更新。
- 判断继续练习、降低难度、补充讲解或结束。
- 生成本轮总结。

### 4.2 会话模式

- `diagnostic`：优先覆盖知识点，快速建立初始掌握度。
- `practice`：优先薄弱知识点，在目标难度附近练习。
- `review`：只选择已到期的复习任务。
- `mock_exam`：会话开始前固定题目集合，过程中不自适应换题。
- `tutor`：针对用户问题检索和讲解；默认不更新掌握度。

MVP 的 UI 可以先暴露前四种模式。`tutor` 在双索引 RAG 稳定后加入。

### 4.3 状态

```python
class LearningAgentState(TypedDict):
    session_id: str
    mode: str
    knowledge_base_id: str
    goal_id: str | None
    current_knowledge_point_id: str | None
    current_question_id: str | None
    answered_question_ids: list[str]
    recent_results: list[dict]
    weak_point_ids: list[str]
    retrieved_chunk_ids: list[str]
    remaining_question_count: int
    next_action: str
    status: str
```

持久化的事实存数据库，checkpoint 只存运行状态。恢复会话时重新读取最新掌握度，避免 checkpoint 中的旧快照覆盖真实数据。

### 4.4 工具

#### `get_learning_context`

返回当前目标、知识点掌握度、到期复习任务、最近答题表现和会话限制。

#### `select_next_question`

输入会话模式、候选知识点和排除题目，使用确定性评分公式返回题目及选择原因。Agent 不自行从数据库挑 ID。

#### `grade_answer`

- 单选和填空先使用确定性规则。
- 简答题由 LLM 对照评分点输出结构化结果。
- 程序将分数钳制到 `[0, max_score]`，并重新计算正确、部分正确或错误状态。

#### `retrieve_material`

只读取题目绑定的来源片段及少量邻接上下文。自由问答时才执行知识库检索。

#### `explain_mistake`

根据题目、回答、缺失评分点和来源片段生成分层解释，必须返回引用。

#### `commit_answer_result`

由 application service 在单一事务中：

1. 写入答题记录。
2. 更新知识点掌握度。
3. 更新或创建复习任务。
4. 更新学习会话计数。

该工具接收经过程序校验的结果，不接受 LLM 任意字段。

#### `build_session_summary`

从已持久化的答题记录生成确定性统计，再由 LLM 将统计组织成简短建议。

### 4.5 在线工作流

```text
load_session
  → load_learning_context
  → choose_knowledge_point
  → select_next_question
  → present_question
  → wait_for_answer
  → grade_answer
  → commit_answer_result
  ├─ 错误且需要讲解 → retrieve_material → explain_mistake
  ├─ 连续错误 → 降低难度或切换基础题
  ├─ 达到本轮目标 → summarize → finish
  └─ 继续 → choose_knowledge_point
```

`wait_for_answer` 是图的中断点。HTTP 接口收到答案后，由 session checkpoint 恢复运行，而不是让一个请求一直占用到整轮结束。

### 4.6 选题算法

候选知识点优先级由程序计算：

```text
knowledge_priority =
    0.45 × (1 - mastery_score)
  + 0.25 × review_due_score
  + 0.20 × goal_weight
  + 0.10 × recent_error_score
```

题目优先级：

```text
question_priority =
    0.45 × difficulty_match
  + 0.25 × freshness
  + 0.20 × source_quality
  + 0.10 × type_diversity
```

规则补充：

- 排除本轮已经作答的题目。
- 优先使用 `active` 且有来源引用的题目。
- `diagnostic` 降低薄弱度权重，提高知识点覆盖率。
- `review` 必须来自到期任务。
- `mock_exam` 在开始时固定抽样和顺序，不能因为答错临时加题。
- 没有合适题目时返回明确的 `no_candidate`，由上层决定生成新题或结束，不允许使用随机字符串进行向量检索。

### 4.7 判题输出

```python
class GradeResult(BaseModel):
    score: float = Field(ge=0)
    max_score: float = Field(gt=0)
    verdict: Literal["correct", "partial", "incorrect"]
    matched_points: list[str]
    missed_points: list[str]
    feedback: str
    confidence: float = Field(ge=0, le=1)
```

程序校验：

- `score = min(max(score, 0), max_score)`。
- `verdict` 根据最终分数重新推导，不盲信模型。
- 模型失败时不记为错误；答题进入 `grading_failed`，允许重试。
- 低置信度判题标记为 `needs_review`，不立即显著降低掌握度。

### 4.8 掌握度更新

MVP 使用可解释的指数更新，不让 LLM 计算：

```text
normalized_score = score / max_score
recent_accuracy = 最近最多 5 次该知识点答题的加权正确率

new_mastery = clamp(
    old_mastery × 0.70
  + normalized_score × 0.20
  + recent_accuracy × 0.10,
  0,
  1
)
```

首次答题时 `old_mastery` 使用 0.30。诊断模式可以使用更大的本次得分权重，但必须作为显式配置并有测试。

需要同时保存 `correct_count`、`wrong_count`、`last_answered_at` 和算法版本，避免只有一个无法解释的分数。

### 4.9 SM-2 复习调度

根据标准化成绩映射质量等级：

- 90%–100%：5。
- 75%–89%：4。
- 60%–74%：3。
- 1%–59%：2。
- 0%：1。

使用标准 SM-2 更新 `repetitions`、`interval_days` 和 `ease_factor`。质量低于 3 时 repetitions 归零，次日复习。算法输出写入 `review_tasks`，并记录算法版本。

### 4.10 讲解策略

错误讲解采用三层结构：

1. 结论：本题正确答案和简短判断。
2. 差距：用户回答命中了什么、遗漏或误解了什么。
3. 证据：引用原文片段、页码和标题路径。

连续两次在同一知识点失败时：

- 先给基础概念解释。
- 下一题降低一个难度等级。
- 不自动生成无限追问题；同一知识点连续追问最多 2 道。

## 5. 双索引 RAG

在 Milvus 中保持两类逻辑独立的 Collection，或者使用统一 Collection 加明确的 `record_type` 分区；MVP 优先采用两个 Collection，避免检索目的混淆。

### 原始资料索引

用于自由问答、判题证据、错题讲解和引用。向量文本是 `document_chunks.content`。

过滤字段：`knowledge_base_id`、`material_id`、`chapter`、`language`。

### 题库索引

用于相似题去重、薄弱点专项练习和题目召回。向量文本至少包含题干，可附带知识点名称和评分点。

过滤字段：`knowledge_base_id`、`knowledge_point_id`、`question_type`、`difficulty`、`status`。

两类索引不能混在同一检索目的中。题目讲解优先读取题目绑定的来源片段，不先进行全库相似度搜索；只有绑定片段不足时才扩展检索。

## 6. 可观测性与测试

### 6.1 题库生成工作流

- 同一输入与模型配置可追踪到相同 run。
- 每个生成题目记录来源 chunk、模型、Prompt 版本和校验结果。
- 测试正常生成、Schema 失败、引用失败、重复题、部分章节失败和幂等重试。
- 建立小型人工审核集，统计结构合法率、来源可验证率、重复率和人工通过率。

### 6.2 学习 Agent

- 每个工具独立单测，LLM 调用使用固定 Stub。
- 状态迁移、会话恢复、重复提交和超时结束必须有测试。
- 判题建立人工标注样本，分别评估填空题和简答题一致率。
- 记录选题原因、模型调用、工具调用、Token、耗时和错误，但不记录密钥和完整敏感正文。

## 7. 实施顺序

1. 定义统一 Document、知识点、题目和判题 Pydantic Schema。
2. 完成资料解析、切块、原文向量入库和 Dense Retrieval 基线。
3. 实现知识点抽取、题目生成、引用验证和人工启用。
4. 建立题库向量索引，完成相似题去重和 metadata 过滤。
5. 实现确定性的选题、判题提交、掌握度和 SM-2。
6. 接入 LangChain 判题 Chain、讲解 Chain 和 Redis 会话状态机。
7. 建立固定评测集后，再决定是否增加 Rerank、混合检索或查询改写。

如果没有链路级测试和确定性状态迁移，不增加 LangGraph 或多 Agent 编排。

## 8. MVP 验收标准

- 题目均能追溯到真实资料片段。
- 生成题目经过 Schema、来源、答案和重复检查。
- 学习 Agent 不直接执行 SQL，不允许模型决定是否写库成功。
- 同一 `submission_id` 重复提交不重复写入答题记录或更新掌握度。
- 简答题判分失败时进入可重试状态，不默认记为错误。
- 每次选题可以说明“为什么现在出这道题”。
- 掌握度和复习时间由可测试算法更新，不由 LLM 自由生成。
- LangGraph、混合检索和 Rerank 在真实实现并完成评测前不写入当前能力。
