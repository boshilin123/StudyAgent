# StudyAgent 项目实施方案

状态：个人项目 MVP 与外部模型评测收尾已完成（P0～P8）  
目标：从旧项目按能力白名单迁移，在新目录中完成可部署、可演示、可评测的个人学习闭环。

## 当前实施状态

- P0～P2 已完成：工程骨架、数据基础、资料解析、异步处理和原文向量索引已实现。
- P3～P5 已完成：题库生成 RAG、客观题学习闭环、自适应选题、引用讲解和可恢复运行态已实现。
- P6 已完成：首页、知识库、题库、学习工作台、进度与复习页面已接入真实 API。
- P7 已完成第一版：可复现检索/题库评测、生产镜像、独立生产 Compose、备份恢复与故障排查文档已落地。
- P8 已完成工程收尾：外部 1024 维 Embedding、资料重建索引、30 条检索基线、59 道题库审计和自动化端到端验收已落地；人工审核率保持待人工填写。

阶段状态以代码和自动化验证结果为准；尚未进入的阶段继续保留为设计，不在简历中表述为已实现能力。

## 1. 实施原则

1. 不整体复制 `eap` 和 `eap-chat`，只迁移已确认有价值的算法、解析器和通用组件。
2. 每个阶段都形成可运行增量，不以“代码已复制”作为完成标准。
3. 数据模型、接口契约和领域规则先行，模型调用最后接入。
4. 先做 Dense Retrieval 基线，再根据评测决定是否增加 Rerank 或混合检索。
5. 题库生成使用固定 LangChain 工作流；学习侧使用受控 Agent，数据库写入由 application service 完成。
6. 外部服务都通过接口适配器隔离，单元测试不依赖真实 LLM、Milvus、Redis 或 MinIO。

```text
StudyAgent/
├── apps/

│   │   ├── study_agent/
```

依赖方向：`api → application → domain`，`infrastructure` 实现 domain/application 声明的端口；`domain` 不依赖 FastAPI、LangChain、SQLAlchemy 或第三方 SDK。

## 3. 阶段拆分

### P0：迁移闸门与工程骨架

工作内容：

- 确认旧代码的个人使用、修改和公开权限。
- 扫描并轮换旧仓库中的密钥、数据库密码、固定公网地址和镜像凭证。
- 初始化 Python、Vue、测试、格式化和基础 CI。
- 建立配置模型、统一日志、异常映射和 `request_id`。
- 创建 Docker Compose 基础服务，但不要求所有业务功能完成。

交付物：

- API `/health/live` 与 `/health/ready`。
- Web 空壳可访问。
- `.env.example` 不包含真实密钥。
- CI 执行静态检查和最小测试。

完成条件：新仓库不依赖旧 `.git`，Secret Scan 无明文密钥，API 和 Web 可在本地启动。

### P1：数据库与知识库 CRUD

工作内容：

- 创建 PostgreSQL 初始迁移。
- 实现知识库、资料、知识点、题目、来源和任务 Repository。
- 完成知识库 CRUD 与资料元数据接口。
- 建立 MinIO Storage 端口及本地文件替代实现。
- 完成上传大小、扩展名、MIME、哈希和幂等校验。

完成条件：能够创建知识库、上传和删除资料；重复上传、存储失败和非法文件有明确错误。

### P2：资料解析与原文索引

工作内容：

- 迁移 PDF、DOCX、PPTX、TXT/Markdown 解析器；XLSX 仅支持结构清晰的表格。
- 转换为统一 LangChain `Document`。
- 按标题、页码和 Token 长度切块，保留来源 metadata。
- 使用 Celery Chain 执行解析、切块、Embedding 和 Milvus upsert。
- 实现任务进度、失败重试、幂等写入和部分失败状态。

完成条件：上传一份 PDF 后能在 PostgreSQL 查询片段，在 Milvus 按知识库和资料过滤召回，并能追溯页码与标题路径。

### P3：题库生成 RAG 工作流

工作内容：

- 统一 LLM 与 Embedding 适配器。
- 用 LangChain Runnable/LCEL 实现知识点抽取、规划、题目生成和修复链。
- 使用 Pydantic Structured Output 约束结果。
- 实现 Schema、来源、答案、选项和评分点校验。
- 建立题库向量索引，执行相似题去重。
- 完成草稿查看、编辑、启用和停用。

完成条件：给定固定资料，能够生成单选、填空和判断题；每道启用题至少有一个真实来源片段，失败任务可定位到具体阶段。简答题留到基础学习闭环稳定后再实现。

### P4：基础学习闭环

工作内容：

- 实现学习会话、当前题目、答题记录和会话恢复。
- 实现单选题、填空题和判断题的确定性判分。
- 在一个事务中提交答题记录、掌握度、复习任务和会话统计。
- 实现 `/start → /answer → /finish` 对应的资源化 API。
- 实现掌握度基线算法和简化 SM-2 复习计划。

完成条件：三种客观题型均可完成一次多轮练习；重复 `submission_id` 不重复计分；会话重启后可以恢复。

### P5：自适应学习 Agent

工作内容：

- 实现 `diagnostic`、`practice`、`review` 和 `mock_exam` 模式。
- 将选题、判题、检索、讲解和提交封装为有类型的工具。
- 使用 Redis 保存受控状态机 checkpoint 与超时信息。
- 实现知识点和题目优先级公式。
- 使用 LangChain 构建基于原文证据的答后讲解链；简答题判分在客观题闭环稳定后另行启用。
- 实现连续错误降难度、最多两次追问和无候选题结束策略。
- 有真实流式讲解需求时，再实现 SSE 事件、心跳和断线重连。
- 实现 SM-2 和带算法版本的掌握度更新。

完成条件：相同状态和配置产生可复现的选题结果；Agent 不能直接写库或构造不存在的 ID；会话中断后可恢复。

### P6：前端闭环

工作内容：

- 首页：待复习、最近学习、整体掌握度。
- 知识库：上传、处理进度和失败提示。
- 题库：筛选、编辑、来源核对和启停。
- 学习工作台：多题型作答、答后讲解、来源引用和会话恢复；确有长文本流式需求时再引入 SSE。
- 学习进度：掌握度、历史记录和复习计划。

完成条件：用户不使用 Swagger 或数据库工具即可走通完整流程；刷新页面不会丢失活动会话。

### P7：评测、部署与简历证据

工作内容：

- 建立固定的检索、题目生成和简答题判分评测集。
- 记录 Recall@K、MRR、题目可溯源率、人工通过率和判题一致率。
- 记录接口和后台任务 P50/P95，但不预设目标数字。
- 完成一键部署、备份恢复和故障排查文档。
- 根据真实代码与评测结果更新简历，不写未实现能力。

完成条件：新环境按照部署文档可启动；评测命令和结果可复现；演示数据不包含旧项目业务或敏感信息。

当前完成说明：已经建立 3 条人工标注检索样本与 3 道现有题目的确定性审计基线，并保存输入、脚本和结果。样本规模不足的指标只作为开发基线，不直接写成泛化性能结论；扩大评测集属于后续持续改进，不阻塞个人 MVP 完成。

### P8：外部模型评测与收尾

工作内容：

- 将开发回退向量替换为外部 1024 维 Embedding，并重建资料与题目双索引。
- 将检索标注集扩展到 30 条，保存独立模型配置和逐条结果。
- 生成并审计至少 50 道有来源的客观题，导出人工审核清单。
- 形成“上传 → 解析 → 检索 → 生成 → 启用 → 学习 → 进度”的自动化验收命令。
- 依据真实结果更新 README、技术文档和简历稿。

完成说明：工程项全部完成；人工审核清单包含 59 道题，但人工通过率必须由人工填写后才能进入简历。

## 4. 旧项目迁移清单模板

每迁移一个能力都记录：

```text
能力名称：
旧文件位置：
保留的算法或通用逻辑：
删除的企业依赖：
新模块位置：
新接口与数据模型：
许可证/授权确认：
安全检查：
测试用例：
迁移状态：待分析 / 迁移中 / 已验证 / 放弃
```

优先迁移：

1. 文本切块和页码、标题元数据提取。
2. 文件上传与解析任务中的纯工具代码。
3. LLM/Embedding 适配器。
4. 结构化生成和 JSON 修复策略。
5. SSE 输出和 Markdown 引用展示组件。

不得迁移：账号、租户、组织、岗位、权限、License、企业报表、SOP 生命周期、第三方成绩推送、固定环境配置和旧密钥。

## 5. 关键技术决策

### PostgreSQL 与 Milvus

PostgreSQL 保存业务事实、状态与引用关系；Milvus 保存原文和题库向量。当前不使用 pgvector 替代 Milvus，因为旧项目中可复用的题库型 RAG、metadata 过滤和向量召回能力集中在 Milvus。

### Redis 与 Celery

Redis 同时承担 Celery Broker、短期任务进度和学习会话状态。Redis 不是长期事实数据库；答题、掌握度和复习计划必须持久化到 PostgreSQL。

### LangChain 与 LangGraph

LangChain 用于模型适配、Retriever、Prompt、Structured Output 和 Runnable。MVP 状态机使用显式 Python + Redis；只有分支复杂度、人工中断和 checkpoint 需求确实超过当前实现时才引入 LangGraph。

## 6. 风险与应对

- **旧代码耦合过深**：只迁移纯函数和适配器，围绕新接口重写业务层。
- **文档解析不稳定**：保存原文件、解析版本和失败页，允许局部重跑。
- **LLM 输出不稳定**：结构化输出、业务校验、有限重试和人工启用。
- **向量数据不一致**：PostgreSQL 保存 `vector_id`，写入使用稳定 ID，提供一致性检查任务。
- **简答题误判**：建立人工标注集，低置信度不显著更新掌握度。
- **范围再次膨胀**：每项新增能力必须说明它解决的 MVP 问题和验收方式。

## 7. 完成定义

一个阶段只有同时满足以下条件才算完成：

- 功能通过接口或页面可验证。
- 数据库迁移可从空库执行。
- 正常、失败、边界和幂等场景有自动化测试。
- 日志可定位失败但不泄露敏感内容。
- 相关接口和技术文档已同步更新。
- 没有以 TODO、假数据或手工改库代替核心链路。
