# StudyAgent 本地开发与部署方案

状态：已实现，启动流程更新于 2026-09-30
说明：Windows 启动脚本兼容 PowerShell 5.1，默认后台运行并自动打开页面。

## 1. 组件

- `web`：Vue 3 静态站点或开发服务器。
- `api`：FastAPI。
- `worker`：Celery Worker，执行解析、向量化和题库生成。
- `postgres`：业务数据。
- `milvus`：原文索引与题库索引。
- `redis`：Celery Broker、任务进度和学习会话状态。
- `minio`：S3 兼容的原始资料对象存储；服务名保持不变，本地镜像使用 RustFS。

MVP 不部署 MongoDB、MySQL、Kubernetes、Helm、Dify、MCP 或 Web Search。

## 2. 环境要求

- Windows 11 + WSL2 或 Linux。
- Docker Engine / Docker Desktop 与 Compose v2。
- Python 3.12。
- Node.js LTS。
- 至少 8 GB 内存；使用本地大模型时按模型额外增加资源。

Windows 上建议将容器数据卷放在 WSL2 文件系统中，减少大量小文件访问的性能损失。

## 3. 配置

`.env.example` 至少包含：

```dotenv
APP_ENV=development
APP_HOST=0.0.0.0
APP_PORT=58000
WEB_PORT=55173

POSTGRES_DB=study_agent
POSTGRES_USER=study_agent
POSTGRES_PASSWORD=change_me
POSTGRES_PORT=55432
DATABASE_URL=postgresql+asyncpg://study_agent:change_me@postgres:5432/study_agent

REDIS_URL=redis://redis:6379/0
CELERY_BROKER_URL=redis://redis:6379/1
CELERY_RESULT_BACKEND=redis://redis:6379/2

MILVUS_URI=http://milvus:19530
MILVUS_DOCUMENT_COLLECTION=study_documents
MILVUS_QUESTION_COLLECTION=study_questions

MINIO_ENDPOINT=minio:9000
MINIO_ACCESS_KEY=change_me
MINIO_SECRET_KEY=change_me
MINIO_BUCKET=study-materials
MINIO_SECURE=false

LLM_BASE_URL=
LLM_API_KEY=
LLM_MODEL=
LLM_TEMPERATURE=0.1
LLM_TIMEOUT_SECONDS=60
LLM_ENABLE_THINKING=false
LLM_STRUCTURED_OUTPUT_METHOD=parser
EMBEDDING_PROVIDER=local
EMBEDDING_BASE_URL=
EMBEDDING_API_KEY=
EMBEDDING_MODEL=
EMBEDDING_DIMENSIONS=384
EMBEDDING_TIMEOUT_SECONDS=30

MAX_UPLOAD_SIZE_MB=100
SESSION_TTL_SECONDS=7200
QUESTION_GENERATION_MAX_CONTEXT_CHARS=24000
LOG_LEVEL=INFO
```

`LLM_STRUCTURED_OUTPUT_METHOD` 可选 `parser`、`function_calling` 或 `json_schema`。DeepSeek 推理模型使用 `parser`；支持工具调用的普通 Qwen 模型可使用 `function_calling`；明确支持 JSON Schema Response Format 的模型才使用 `json_schema`。

真实 `.env` 不提交仓库。生产环境使用 Secret 管理，不把密钥写入 Compose 文件或镜像。

## 4. Compose 要求

- 所有持久化服务使用命名卷。
- PostgreSQL、Redis、Milvus 和 S3 兼容对象存储配置健康检查。
- `api` 在数据库迁移成功后启动。
- `worker` 与 `api` 使用同一代码镜像和配置，但执行不同入口。
- Web 只访问 API，不直接连接数据库和对象存储。
- 本地端口为 Web `55173`、API `58000`、PostgreSQL `55432`、Redis `56379`、Milvus `59530`、对象存储 API `59000`、对象存储控制台 `59001`。
- 这些端口仅用于本地开发，生产环境除 Web/API/对象存储控制台外不应直接暴露基础组件。

建议启动顺序：

```text
postgres / redis / minio / milvus
  → database migration
  → api / worker
  → web
```

## 5. 首次启动流程

先打开 Docker Desktop，再执行（可从任意目录运行）：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File D:\Study\StudyAgent\scripts\dev.ps1
```

脚本会在缺少配置时复制 `.env.example`，后台启动服务并等待健康检查，验证 Web 与 API 代理可访问后自动打开浏览器。首次缺少镜像时会构建，启动期间仍有有限的进度消息，但不会持续输出 Milvus 等组件日志。真实模型功能需要先配置 `.env` 中的密钥。

支持 `-NoBrowser`、`-FollowLogs`（仅 API/Worker/Web）和 `-Rebuild`。数据库迁移由 API 启动入口执行，存储 bucket 和向量 Collection 在业务使用时幂等创建或校验。

关闭启动终端、关闭浏览器或退出日志跟踪，不等于停止后台 Docker 容器。停止服务但保留数据：

```powershell
docker compose --project-directory D:\Study\StudyAgent stop
```

不要为了停止项目执行 `down -v`，它会删除数据卷。确认运行状态可使用 `docker compose --project-directory D:\Study\StudyAgent ps`。

## 6. 健康检查

- `GET /api/health/live`：进程存活，不检查外部依赖。
- `GET /api/health/ready`：检查 PostgreSQL、Redis、Broker、Milvus 和存储，任一失败或超时返回 503；不检查外部 LLM。
- Celery 提供独立 ping 或任务探针。

readiness 示例：

```json
{
  "status": "ok",
  "dependencies": {
    "postgresql": "up",
    "redis": "up",
    "milvus": "up",
    "broker": "up",
    "storage": "up"
  }
}
```

LLM 不可用时，资料浏览、历史查询和客观题判分仍可用；生成任务可能失败，讲解会降级。当前不提供简答题判分。

## 7. 数据持久化与备份

需要备份：

- PostgreSQL：业务事实和向量 ID 映射。
- S3 兼容对象存储：原始资料。
- Milvus：向量数据；也可通过 PostgreSQL 片段和 Embedding 模型重建。
- 配置中的模型、Embedding、切块和 Prompt 版本。

Redis 不作为长期备份对象。丢失 Redis 后，活动会话可从 PostgreSQL 重建；历史答题、掌握度和复习计划保留在数据库中。

恢复顺序：PostgreSQL → S3 兼容对象存储 → Milvus；恢复后运行一致性检查，确认 chunk 与 vector ID 对应。

## 8. 日志与故障排查

所有服务输出结构化日志，至少包含时间、级别、服务、`request_id`、`job_id` 或 `run_id`、错误码和耗时。

常见检查顺序：

1. `docker compose ps` 查看健康状态。
2. 检查 API 和 Worker 日志中的同一 `request_id` / `job_id`。
3. 查询 PostgreSQL 任务状态和安全错误摘要。
4. 检查对象存储中的原始资料是否存在。
5. 使用稳定 vector ID 检查 Milvus 数据。
6. 最后检查模型服务、超时和限流。

不得在日志或排障截图中公开 `.env`、API Key、完整 Prompt、用户资料全文和数据库备份。

## 9. 更新与回滚

更新前：

- 备份 PostgreSQL 和 S3 兼容对象存储。
- 阅读 Alembic 迁移是否可回滚。
- 保存当前镜像标签和配置版本。

更新顺序：迁移数据库 → 更新 API/Worker → 更新 Web。破坏性迁移必须使用“新增字段 → 双写/迁移数据 → 切换读取 → 后续删除”的方式，不在一次发布中直接删除仍被旧版本使用的字段。

应用回滚不能自动回滚包含数据损失的数据库迁移。此类迁移必须先恢复备份或执行经过验证的 downgrade。
