# StudyAgent 生产部署与故障排查

## 1. 适用边界

本文适用于单用户或可信内网部署。P10 提供共享 Bearer 访问令牌，但没有账号、资源所有权、租户隔离、上传病毒扫描和公网限流，因此不能直接作为开放互联网多用户服务。

## 2. 启动生产编排

先复制并修改配置，确保数据库、对象存储、LLM 和 Embedding 密钥不是示例值，并设置至少 32 位 URL-safe 的 `API_ACCESS_TOKEN`（建议使用密码管理器生成，不使用示例固定值）：

```powershell
Copy-Item .env.example .env
## 编辑 .env，设置 API_ACCESS_TOKEN 与服务密钥后再执行以下命令
docker compose -f compose.production.yaml config
docker compose -f compose.production.yaml up -d --build
docker compose -f compose.production.yaml ps
```

访问 <http://localhost:55173> 后，在右上角“访问令牌”录入配置值。生产 Web 使用独立的 Node 静态服务提供构建产物，并将 `/api/` 转发到内部 API；PostgreSQL、Redis、Milvus、etcd 和对象存储不映射宿主机端口。公网入口必须配置 HTTPS，不能通过明文 HTTP 传输令牌。

停止服务但保留数据：

```powershell
docker compose -f compose.production.yaml down
```

不要在没有完整备份时执行 `down -v`，它会删除命名卷中的业务数据。

## 3. 发布前检查

```powershell
Set-Location apps/api
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check study_agent tests
Set-Location ..\..\apps\web
npm.cmd run typecheck
npm.cmd run build
```

随后确认：

- `.env` 未进入版本控制或镜像构建上下文。
- `docker compose -f compose.production.yaml config` 没有缺失变量。
- `/api/health/live` 与 `/api/health/ready` 返回成功。
- 数据库迁移版本为 Alembic head。
- Worker 已注册资料处理和题库生成任务。

## 4. 备份范围

### PostgreSQL

PostgreSQL 是业务事实来源，必须优先备份：

```powershell
New-Item -ItemType Directory -Force backups\2026-09-28
docker compose -f compose.production.yaml exec -T postgres pg_dump -U study_agent -d study_agent -Fc -f /tmp/study_agent.dump
$postgresId = docker compose -f compose.production.yaml ps -q postgres
docker cp "${postgresId}:/tmp/study_agent.dump" backups\2026-09-28\study_agent.dump
```

### 原始资料

在没有上传或解析任务运行时复制对象存储数据：

```powershell
$minioId = docker compose -f compose.production.yaml ps -q minio
New-Item -ItemType Directory -Force backups\2026-09-28\object-storage
docker cp "${minioId}:/data/." backups\2026-09-28\object-storage
```

### 向量索引与配置

- Milvus 数据可以额外做卷快照，也可以通过 PostgreSQL 片段、题目和相同 Embedding 配置重建。
- 记录模型名称、Embedding 维度、切块参数和 Prompt 版本。
- 不要把包含真实 API Key 的 `.env` 放进普通备份归档；使用 Secret 管理工具单独备份。
- Redis 不作为长期事实备份对象。

## 5. 恢复演练

恢复应先在新项目名或隔离机器验证，禁止直接覆盖唯一生产环境。

1. 使用相同版本镜像启动空 PostgreSQL 与对象存储。
2. 将对象存储备份复制到新容器 `/data`，重启对象存储并检查 bucket。
3. 把 `study_agent.dump` 复制到 PostgreSQL 容器。
4. 执行 `pg_restore --clean --if-exists` 恢复数据库；该操作会覆盖目标数据库，只能对已确认的隔离目标执行。
5. 启动 Milvus、API 与 Worker，使用原 Embedding 配置重建缺失索引。
6. 执行 Alembic upgrade、健康检查和主链路冒烟测试。
7. 对比知识库、资料、片段、题目、答题记录和掌握度数量。

恢复命令示例中的目标容器和数据库名必须先人工确认，不提供无确认的一键覆盖脚本。

## 6. 常见故障

### 前端仍显示“框架已就绪”

这是 Vite 开发服务器的旧模块缓存。确认容器内源码已经更新后执行：

```powershell
docker compose restart web
```

浏览器再使用 `Ctrl+F5` 强制刷新。可以访问 `/src/router/index.ts`，确认业务路由不再指向 `PlaceholderView.vue`。

### 中文内容显示为连续问号

如果页面固定标题正常、只有知识库名称或描述显示为 `????`，通常不是前端字体问题，而是测试数据在写入数据库前已经被终端错误编码替换为 ASCII 问号。可以查询 PostgreSQL 字节内容确认：问号对应十六进制 `3f`，原中文已经无法从数据库自动恢复。

Windows 下创建中文测试数据时，确保请求体明确使用 UTF-8。例如 Python 客户端应使用：

```python
json.dumps(payload, ensure_ascii=False).encode("utf-8")
```

并设置 `Content-Type: application/json`。修复现有数据时通过知识库更新接口重新提交正确中文，不要只调整浏览器编码。项目的 API 测试包含中文名称和描述的 UTF-8 往返验证。

### 页面存在但 API 请求失败

```powershell
docker compose ps api web
docker compose logs --tail=100 api web
Invoke-RestMethod http://localhost:55173/api/health/live
```

开发环境由 Vite 代理，生产环境由内置静态服务器代理。不要让浏览器直接访问容器内部主机名 `api:8000`。

### 上传后一直处于排队或解析中

```powershell
docker compose ps worker redis minio milvus
docker compose logs --tail=200 worker
```

根据上传响应中的 `job.id` 查询 `/api/ingestion-jobs/{id}`，重点检查 `stage`、`progress`、`error_code`。确认 Worker、Redis、对象存储和 Milvus 都可用。

### 题库生成失败

检查资料必须为 `ready`，再根据题库生成任务的阶段定位。外部 LLM 需要检查模型名、超时、限流以及结构化输出方式；DeepSeek 推理模型使用 `parser`。

### Milvus 维度不一致

Collection 创建后不能混用不同维度。确认 `EMBEDDING_DIMENSIONS` 与服务真实输出一致；切换模型或维度时应创建新 Collection 或清空并完整重建索引，不能继续写入旧 Collection。

### 活动会话无法恢复

先查询 PostgreSQL 会话事实，再检查 Redis `study:session:{session_id}:state`。Redis 丢失时查询会话接口会尝试重建；若题目已停用导致没有候选题，应结束本轮重新开始。

## 7. 更新与回滚

更新前备份 PostgreSQL 和对象存储，保存当前镜像标签与配置摘要。按“数据库迁移 → API/Worker → Web”顺序发布。

应用镜像可以回滚，包含数据损失的数据库迁移不能盲目 downgrade。此类变更必须采用新增字段、迁移数据、切换读取、后续版本删除的分阶段方式。
